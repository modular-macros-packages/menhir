# Developer Guide

This guide is intended for new Menhir developers,
and is supposed explain how things work.

## Organization of the Code

The code is organized in several libraries and directories:

* The directories
  [`bitsets`](bitsets/),
  [`fix`](fix/),
  and
  [`pprint`](pprint/)
  contain copies of the external libraries by the same names.
  In Dune speak, these libraries are "vendored".

* The library `MenhirLib`, which resides in [`lib`](lib/),
  is the runtime support library for the parsers
  generated by Menhir in `--table` mode.

* The library `MenhirSdk`, which resides in [`sdk`](sdk/),
  allows reading automaton description (`.cmly`) files.

* The library `MenhirCST`, which resides in [`cst`](cst/),
  is the runtime support library for the unparsing API,
  which is described in [this paper](https://cambium.inria.fr/~fpottier/publis/pottier-unparsing-2024.pdf).

* The internal library [`base`](base/)
  provides general-purpose modules,
  which are essentially independent of Menhir.
  The modules [`BaseTypes`](base/BaseTypes.ml) and
  [`BaseAPI`](base/BaseAPI.ml)
  define several types and signatures of interest.

* The internal library [`front`](front/)
  contains many modules that form Menhir's front-end.
  The modules [`FrontTypes`](front/FrontTypes.ml) and
  [`FrontAPI`](front/FrontAPI.ml)
  define several types and signatures of interest.
  In the front-end, a grammar is described by the types
  [`Syntax.partial_grammar`](front/Syntax.ml),
  [`Syntax.grammar`](front/Syntax.ml),
  or
  [`PlainSyntax.grammar`](front/PlainSyntax.ml).

* The internal library [`middle`](middle/)
  contains many modules that form Menhir's middle-end.
  The module [`MiddleAPI`](middle/MiddleAPI.ml)
  defines several signatures of interest.
  In the middle-end, a grammar is described by the signature `GRAMMAR`.
  An LR(0) automaton is described by the signature `LR0`.
  An LR(1) automaton is described by the signature `LR1`.

* The internal library [`driver`](driver/)
  bundles Menhir's lexer and parser.
  In Dune speak, it is a virtual library.
  There are three implementations of this library
  in `driver/stage1`, `driver/stage2`, and `driver/stage3`.
  The stage 1 parser is constructed using `ocamlyacc`.
  The stage 2 parser is constructed using Menhir (built in stage 1).
  The stage 3 parser is constructed using Menhir (built in stage 2);
  we check that the stage 2 and stage 3 parsers are identical.

* The internal library [`body`](body/)
  contains the back-ends
  and the modules that drive Menhir.
  The three back-ends are in the three modules
  [`CodeBackend`](src/CodeBackend.ml),
  [`TableBackend`](src/TableBackend.ml), and
  [`CoqBackend`](src/CoqBackend.ml).
  The code back-end relies on the intermediate language StackLang,
  whose implementation resides in [`src/StackLang`](src/StackLang/).

* The modules that drive Menhir have side effects
  and are executed in a specific order.

    | Module                | Task |
    | --------------------- | ---- |
    | Settings              | parses the command line |
    | Front                 | reads the `.mly` files; |
    |                       |  deals with several commands; |
    |                       | transforms the grammar into `PlainSyntax` format |
    | Grammar               | transforms the grammar into `GRAMMAR` format |
    | Lr0                   | deals with several commands; |
    |                       | constructs the LR(0) automaton |
    | Lr1                   | constructs the LR(1) automaton |
    | Freeze                | deals with several commands |
    | Invariant             | performs several analyses of the LR(1) automaton |
    | Back                  | invokes the desired back-end; |
    |                       | produces the output and exits |

* The executable programs are built in `executable/stage1` and `executable/stage2`.
  There is no code there; the complete program is obtained by linking the libraries
  together. The executable file that is installed under the name `menhir` is
  `executable/stage2/main.exe`.

## How Menhir is Built

Menhir is built by `dune`. The build process takes place in several stages:

* A preliminary version of Menhir, referred to as "stage 1", is built.
  In order to build Menhir's parser, `ocamlyacc` is used.
  The parser and driver in `src/stage1` are used.

* The final version of Menhir, referred to as "stage 2", is built.
  In order to build Menhir's parser,
  (the stage 1 version of) Menhir itself is used.
  The parser and driver in `src/stage2` are used.

* As a sanity check, another version of Menhir,
  referred to as "stage 3", is built.
  In order to build Menhir's parser, the stage-2 Menhir is used.
  The parser and driver in `src/stage2` are used again.
  We check that a fixed point is reached, that is,
  the stage-2 and stage-3 versions of Menhir
  behave in the same way when applied to Menhir's grammar.

## Testing

To run all tests, type `make test` in the root directory.

To run the benchmarks, type `make benchmarks` in the root directory.

The tests in the directory `test/static` test that Menhir seems to run
properly, but do not test the generated parser.

* The subdirectory `test/static/good` contains a number of correct `.mly` files.
  We check that Menhir accepts these files and
  compare the output of `menhir --only-preprocess` against an expected output.
  We do not check that Menhir actually produces a working parser.

* The subdirectory `test/static/bad` contains a number of incorrect `.mly` files.
  We checks that Menhir rejects these files
  and produces the expected error message.

* The subdirectory `test/static/merge` tests the command `--merge-errors`.

* The subdirectory `test/static/merge` tests the command `--list-errors`.

The tests in the directory `test/dynamic` test the generated parsers.
See the [README](test/dynamic/README.md) file there.

The demos in the directory `demos` also contain tests.

## Releasing

Prior to making a release, please take the following actions:

* Make sure `CHANGES.md` and `coq-menhirlib/CHANGES.md` have been properly updated.

* Make sure that you are on the `master` branch and have
  committed everything. No uncommitted files should remain.

* Run `make test` and `make demos` and `make versions`
  to make sure that the tests succeed
  and that Menhir can be compiled under all supported versions of OCaml.

* Run `make benchmarks` and have a look at the performance figures to
  make sure that they are still in the right ballpark.

* Test the `opam` package by running `make pin`
  (possibly in a dedicated switch, so as to avoid clobbering your
  current installation of Menhir).
  If `make pin` succeeds, then its effect can be undone by `make unpin`.

To create a release, run `make release`. This creates a release and commits it
to a fresh release branch. It also commits a copy of the documentation to the
master branch. The effects of this command are local; nothing is pushed or
published.

If you are happy with the outcome of `make release`, you can then proceed to
the following three steps:

* Run `make publish` to push the new release to `gitlab.inria.fr`.

* Run `make export` to upload the documentation to Menhir's home page.

* Run `make opam` to create and publish a new `opam` package.

If you are not happy with the outcome of `make release`, you can undo it
by typing `make undo`.
